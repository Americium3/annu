# Recommender experiments on golden_eval (dev split)
Generated by `python -m experiments.report`. Every system receives only the user's service text and location text (`service_label`, `location_text`) and is scored against `workspace.golden_eval.judgments_dev` (29 queries, 28 with a recommendable facility, 1 'desert'). The test split was never read.
## Summary
- **Best system = the shipped defaults (`E9_shipped_defaults`)**: location resolver + v2 stage-1 candidates + minimum pool of 3 + multi-service intent + plausibility/source down-weights + 'evidence' solid gate + rules ranking (proof x closeness, no text model).
- The large gains came from stage 1 and query understanding (location, candidates, pool size, intent), not from the reranker. Every text model (BM25, bi-encoder, 3 cross-encoders, NLI, Qwen2.5 0.5B as a yes/no verifier, ensemble) was tried on the same candidates; none gives a gain whose bootstrap interval excludes 0, and single cross-encoders lower P@3, so ranking stays rules-only (cheaper, deterministic, explainable).
- Weight/distance/urgency tuning does not survive leave-one-query-out CV, so defaults were kept.

## How to read this
- Labels are silver standard: produced by rules (`golden_eval.label_rules`), not by people. The recommender does not reuse those rules. Two v2 down-weights (a name announcing another specialty; inpatient-only services at a clinic) resemble checks in the label rules, so E6's small gain may be partly optimistic.
- 28 answerable queries: differences below about 0.03 are within noise (see the bootstrap intervals).
- `_j` metrics skip unjudged results; plain metrics count them as not relevant.
- Reproduce: `python experiments/export_data.py`, `python pipeline/service_index_v2.py ...`, `python -m experiments.run_golden`, `python -m experiments.grid`, `python -m experiments.rules_grid`, `python -m experiments.report`.
